## 阶段一：原型期（2026-05）

### 决策 1：评分基准从哪来？

**上下文**：手头有一批真实业务 QA 对（问题 + 标准答案），但标准答案是自然语言段落，LLM 无法直接对"回答 vs 段落"打一个稳定的分。

**方案 A**：让 LLM 直接对照标准答案段落打分。——风险：标准答案段落含大量叙述性内容，模型难以判定哪些是得分点，评分方差大。

**方案 B（采用）**：先用 LLM 把每对 QA 拆成结构化评分要点（必答点/选答点/参考文件），评分时逐要点判定。——要点提取一次性完成、人工可复核，评分变成可解释的逐点判定。

**教训**：评分可解释性不是额外开销，是实验可信度的前提。后续评分引擎（rubric/strict 双尺度、扣除多余内容、冲突点归零）都是这个思路的延伸。

### 决策 2：切分模块自研还是用库？

当时选了自研。**这是一个后来被证伪的决策**：自研切分器无法形成策略矩阵，对比两种切法就需要两套代码路径，测量结果不可比。阶段二的整体迁移就是对这个决策的修正。值得记录的不是"自研错了"，而是：**当一个组件是实验变量本身时，它必须满足注册-替换-对比三件事，自研方案天然做不到。**

## 阶段二：工程化（2026-07）

### 决策 3：声明式策略注册（YAML）

**上下文**：策略数量开始膨胀（切分器 × 检索器 × 重排器的笛卡尔积），硬编码注册会让每个实验都改代码。

**方案 A**：工厂模式硬编码字典。——每次加策略动框架代码。
**方案 B（采用）**：`strategies.yaml` 声明式定义 + `core/registry.py` 动态类加载。策略即数据，实验维度直接在 CLI 参数展开（`--chunkers a,b,c`）。

**价值**：这一决策让后文所有大规模对比实验（13 切分器批量构建、2×2 矩阵、Multi-Query）成为"改 YAML + 一个命令行"的事。**把实验变量变成数据，是能规模化做实验的前提。**

### 决策 4：混合检索的实现位置

**方案 A**：Python 侧取回 dense + sparse 两份结果做融合归并。——灵活但慢，且两份候选集要先搬回 Python。
**方案 B（采用）**：入库同时写 dense + sparse 双向量，检索时用 Qdrant 原生 `Prefetch`（dense/sparse 并行预取）+ `FusionQuery(RRF)` 在服务端融合。——一份网络往返完成混合检索；RRF 参数 `k=60` 可调。

**取舍记录**：代价是依赖 Qdrant 版本特性与该特定实现路径；后续发现 `strategies.yaml` 里定义的 Python 侧融合检索器（Weighted/RRF）与实际检索路径不一致——**YAML 定义与实际执行路径的漂移**，已作为已知限制如实声明（README §8）。

### 决策 5：dense+sparse 配套的稀疏词表怎么办

jieba 分词 + BM25 词表在入库时按语料拟合，词表持久化到 `datasets/{kb}/_sparse_{chunker}.json`。检索时若词表缺失则稀疏检索静默降级为纯 dense——**静默降级是个双刃剑**：保证了 demo 与复现的流畅，但也会掩盖配置错误。这个 trade-off 的选择依据是：评测框架的第一优先级是"实验能跑完"而不是"失败要响亮"。

### 本阶段埋下的隐患

`header_aware_h6` 策略把 Markdown 标题链注入块内容。"章节结构帮助检索"这个假设此时已经进入系统**且没有对照组**。阶段四的实验证明这个直觉在当时的语料上是负资产（-13~16pp）。回顾起来，如果阶段二就做 2×2，阶段三的整个分层架构冒险本可以避免——**这就是"先测量"为什么值钱。**

## 阶段三：分层检索实验（2026-08）

### 决策 6：给元数据一个"正确"的用法——分层路由

**上下文**：受业界分层摘要检索路线启发。想法很完整：文件/章节摘要先做一层路由（Layer A 向量检索定位相关章节），内容检索（Layer B）在定位结果之上进行，最后双路融合。元数据从"块内容的附属品"升级为"独立导航层"。

### 决策 7：为什么要放弃它

放弃它不是因为实现困难（实现已完成并跑通三路召回对比），而是三个具体的负面证据：

1. **级联故障**：Layer A 选错，Layer B 无法挽回。分层系统的效果被钉死在"每层的最小值"上。
2. **Layer A 召回成为新瓶颈**：它不贡献答案内容，却决定了系统上限。这一层的成本-收益没有正证据。
3. **变量污染**：分层系统里"切分方式""元数据质量""路由阈值"全部纠缠在一起。系统越复杂，越无法回答"结构信息到底有没有用"这一原始问题。

**最重要的元认知**：我意识到自己在**用架构复杂度对冲假设的不确定**——不确定假设对不对时，人倾向于"多做点什么"。而正确做法恰恰相反：收缩变量，做最小可证伪实验。这个认识直接催生了 2×2 矩阵设计。

## 阶段四：元数据增强主线（2026-08）

### 决策 8：2×2 矩阵设计

两个正交操作化变量：

- **切分方式**：`章节预切`（detect_sections 先切章节边界，章内再切块）vs `全文直切`（忽略章节、全文横向切）。这是"是否利用结构"的干净操作化。
- **元数据注入**：build 时为每块拼入 `file_type + file_summary + section_summary` 文本后再 embed vs 不拼。这是"元数据入库"的直接效应测量。

实验操作要点：

- 四格使用同一 embedding 模型、同一检索器（hybrid top5）、同一测试集（112 题高质量子集）——只动目标变量；
- 效应分解：固定一侧做差（raw − meta 得切分效应；raw_meta − raw_pure 得元数据效应），两个效应在四个格子间交叉验证；
- 结果在更大测试集（143/183 题）上做方向性复核。

### 决策 9：逐题差异归因（不是只看均值）

2×2 给出均值差后，进一步做了逐题胜负统计（哪几题 meta 胜、哪几题 raw 胜），把 +15.2pp 的均值差化为可解释的题面模式。这引出了 §4.4 的三个归因（块被章节边界切碎、跨条引用被切断、块长分布恶化）。**均值告诉你"什么赢"，归因告诉你"为什么赢"——后者才是可迁移的知识。**

### 决策 10：测量工具校验（autojunk 伪影的完整追查链）

1. 现象：拼接口径出现可疑高分，极端 case 下"正确答案与自身匹配率 <100%"——逻辑上不可能，因此必然是测量 bug；
2. 定位：`difflib.SequenceMatcher` 默认开启 autojunk，高频短片段被当垃圾剔除；政策文本的高频套话恰好命中；
3. 修复：拼接口径 `autojunk=False`；合并口径从"拼接后对齐"重构为"逐块对齐取 max"，从算法层面绕开；
4. 验证：修复后重跑全量对比，四口径之间恢复预期的单调关系（单块 ≤ 合并 ≤ 拼接）。

代码中该段注释保留了这个故事（`pipeline/recall.py`），作为对后人的警示：**评测框架不会报错，只会安静地扭曲一切结论。**

### 决策 11：Multi-Query 负结果的记录方式

Multi-Query 融合实验得到 0~-0.7pp 之后，没有"再调调 prompt 试试能不能转正"，而是直接收尾、写明结论与解释（瓶颈在块内容完整性而非查询多样性）。理由是：**在一个已被证伪的方向上继续调参，是用工程工时购买心理安慰。** 该负结果写进了 README §3.5 与实验数据表。

## 给下一阶段的备忘

- 在不同语料（非政策法规）上复现 2×2——切分效应是否同样主导，是判断这些结论可外推性的唯一方法；
- 表格密集文档需要独立的切分研究（当前天花板的主要来源）；
- 元数据的出路大概率在路由型检索（多领域混合语料下的先验过滤），而非块内容注入；
- 任何新召回口径上线前，先用"答案与自身匹配 = 100%"这种构造性用例做测量仪器校验。
