# RAG-Pro：元数据入库 RAG 研究

> 一个面向政策/法规类文档的 RAG 切片策略评估框架。核心研究问题只有一个：**在「章节检测 + 元数据注入」这条被普遍认为有效的路上，究竟是什么在影响检索召回率？**
>
> 答案是反直觉的：**切分方式决定一切（+13~16pp），而精心设计的元数据注入收益甚微（0~+2.7pp）**。最佳组合「全文直切 + 元数据」内容召回 84.8%。

---

## 1. 为什么做这个研究

### 1.1 业务起点

需求来自一个具体业务场景：**给政策/法规类文档做问答系统**。这类文档有鲜明的结构特征：

- 多级标题树（章/节/条/款），条款编号规整（"第一条"）；
- 条文短而语义独立，但答案经常跨条引用（"按照第三章第七条执行"）；
- 表格密集（系数表、定额表、清单表），数字是答案的核心；
- 单份文件几十页，语料库动辄几十上百份文件。

当时手头已有一批真实业务 QA 对（问题和标准答案）。很自然地产生了一个假设——这个假设几乎是所有做文档 RAG 的人都默认成立的：

> **"既然文档有结构，把结构信息（章节归属、章节摘要、文件摘要）注入检索，理应提升效果。"**

我的做法不同之处在于：**没有直接把这个假设当作优化项去做，而是把它变成了一个可证伪的实验问题。** 这是整个项目最重要的一次决策，后面的所有工作（包括最终那个反直觉的结论）都源于此。

### 1.2 研究问题定义

把「结构化预处理」拆成两个**正交变量**：

| 变量 | 含义 | 取值 |
|------|------|------|
| **切分方式** | 切分器是否感知文档的章节结构 | 章节预切（先按标题树切章节，再在章内切块） vs 全文直切（忽略章节边界，全文横向切） |
| **元数据注入** | 块的向量化内容是否混入 LLM 生成的元数据 | 注入（file_type / file_summary / section_summary 拼入块文本一起 embed） vs 不注入 |

两者构成 2×2 控制变量矩阵。在此基础上，再叠加切分粒度（1100/1500 字）、重叠窗口（0/150/200 字）等次级变量。

配套的测量基础设施：4 个口径的召回率计算、双尺度 LLM 评分、可复现的实验编排。**测量是所有结论的前提**——这是我在研究过程中反复得到强化的第二条经验（第一条在 1.1）。

## 2. 研究历程：四阶段演进

这段历史不是文档考古，而是四个连续的工程决策。每个阶段的"遗留问题"就是下一个阶段的动机。

### 阶段一：原型期（2026-05）—— 先解决"怎么测"

**当时的问题**：有 QA 数据，想对比不同切分方式的效果，但发现**连"回答质量"都没有一个可计算的度量**。

**做法**：自研最小闭环——从 QA 对提取评分要点（必答点/选答点/参考文件）→ 检索 → 生成 → LLM 按要点打分。切分模块全自研，Qdrant 嵌入式模式。

**关键教训**：

1. 自研切分器没有策略矩阵可言——想对比三种切法就得改代码、重跑、人工对齐结果。**手段和评价对象混在一起，测量不可比。**
2. LLM 评分的主观性必须被控制：要点提取要有流程（`prepare`），评分要有固定提示词和打分规则，否则同一份回答今天 85 分明天 70 分，实验结论不可复现。

**演进动因**：度量跑通了，但"换策略"的成本高到无法做大规模对比实验。

### 阶段二：工程化（2026-07）—— 用标准件搭建策略矩阵

**当时的问题**：需要把"切分策略"变成**可插拔、可注册、可批量对比**的一等公民。

**做法**：整体迁移到 LangChain 生态：

- 切分器：`RecursiveCharacterTextSplitter` / `TokenTextSplitter` / `MarkdownHeaderTextSplitter` 标准件 + 自研 `LLMIndexSplitter`（段落 + LLM 索引）、`ParentChildSplitter`（父块 + 句子子块，embed 子块返回父块）；
- **YAML 声明式注册**：13 个切分器、4 个检索器、3 个重排器全部写在 `strategies.yaml`，运行时动态类加载。新增一个策略 = 改 YAML + 实现一个类，框架代码零改动；
- Qdrant 服务模式 + **dense/sparse 双向量**（BM25 稀疏向量由 jieba 分词拟合词表生成）+ Qdrant 原生 RRF 混合检索；
- 工程健壮性：429 退避重试、嵌入批次控制、并发构建、失败元数据重试。

**关键教训**：这个阶段埋了一个隐患——`header_aware_h6` 把章节标题链注入块内容。"用章节结构帮助检索"这个**未经验证的假设，已经无声无息地混进了系统**，而且没有对照组。

**演进动因**：策略矩阵就绪，13 个切分器可以一键批量对比了。但结构信息究竟是"资产"还是"负债"，依然没有答案。

### 阶段三：分层检索实验（2026-08）—— 一次被数据劝退的架构冒险

**当时的问题**：受业界分层摘要检索路线的启发，试图把元数据做成一等公民的**导航层**：Layer A 用文件/章节摘要向量做路由（先定位相关章节），Layer B 在定位到的章节内做内容检索，双路融合。

**做法**：两层索引、路由 + 内容检索 + 融合的完整实现。

**关键教训（这个阶段我学到的比前两个阶段加起来都多）**：

1. **分层引入级联故障**：路由错误会放大——Layer A 选错了章节，Layer B 检索得再好也救不回来。分层系统的效果卡在每一层的最小值上。
2. **Layer A 自身召回成为新瓶颈**，而且它还不直接贡献答案内容——这层开销没有端到端收益的证据。
3. 最深的反思：**我在"堆架构"而不是"测假设"**。结构信息到底有没有用这个问题，被淹没在越来越复杂的系统里了。

**演进动因**：果断收缩。与其再加层，不如做一个干净的控制变量实验，把「切分方式」和「元数据注入」彻底正交化——这就是本仓库的主体工作。

### 阶段四：元数据增强主线（2026-08）—— 2×2 矩阵与反直觉结论

**做法**：2×2 矩阵实验（见 §4）。四个组合：章节预切×元数据、章节预切×无元数据、全文直切×元数据、全文直切×无元数据，在 112 题高质量测试集上跑 hybrid top-5 召回，并做效应分解。

**结果（详见 §5）**：切分方式效应 +13~16pp，元数据效应 0~+2.7pp。**「章节结构对检索有帮助」这个从阶段二就混进系统的假设，被数据基本否定了。**

这个结论直接改变了后续技术路线：与其在元数据注入上继续投入，不如把精力放在切分方式上（粒度、重叠、对表格密集文档的处理）。

## 3. 方法论与实验设计

### 3.1 测试集

测试集是评测的根基。列格式：`问题 | 正确回答 | 必答点 | 选答点 | 参考文件`。

- **407 题汇总测试集**：全量业务问答对（含 72 题后增补），用于大规模验证；
- **112 题高质量子集**：从全量中人工筛选出"问题无歧义、答案唯一、参考文件明确"的题，用于 2×2 矩阵等精细对照实验——**精细实验用干净子集，避免噪声淹没信号**；
- 必答点/选答点由 `prepare` 命令用 LLM 从问答对中提取，人工复核。

### 3.2 召回率四口径：为什么需要四个？

单一口径会系统性误导结论。以"答案文本在检索块中的覆盖率"为例：

| 口径 | 定义 | 特点 |
|------|------|------|
| **单块召回** | 任一单块与答案的汉字序列相似度 ≥ 阈值 | 最严格。但答案常跨两块分布，会系统性误判漏召回 |
| **合并召回** | top-k 各块分别与答案对齐，取最大相似度 | 消除了"答案跨块"的误判。**最具代表性** |
| **拼接召回** | top-k 全文拼接后与答案对齐 | 最宽松，衡量"大杂烩"能否碰巧覆盖答案 |
| **文件召回** | 检索结果中是否命中正确答案的参考文件 | 衡量"找对文档没有"，与内容召回正交 |

核心口径 = 合并召回 + 文件召回。相似度用中文汉字序列的 `SequenceMatcher`，阈值 70%（对比试验中配套 90% 观察结论稳健性）。

### 3.3 测量工具的 bug 比模型的 bug 更危险：autojunk 伪影

实验中期，拼接召回率出现**可疑的异常值**——甚至出现过"正确答案与自己都匹配不到 100%"的荒谬结果。追问下去发现是 `difflib.SequenceMatcher` 的 **autojunk 启发式**：它会先把序列中的高频重复片段标记为"垃圾"剔除。而政策文本恰恰充满高频套话（"应当按照""执行下列规定"），这些片段被当成 junk 剔除后，相似度被系统性扭曲。

**修正**：拼接口径强制 `autojunk=False`；同时合并口径从"拼接全文后对齐"改为"逐块 max"——从设计上绕开 autojunk，而不是依赖参数修补。

**这个坑的价值**：评测框架的 bug 不会报错，只会悄悄扭曲**所有**实验结论。它教会我：测量仪器本身要用已知答案做校验（golden test 思路），而不是假设它是对的。相关代码与注释保留在 `pipeline/recall.py`。

### 3.4 LLM 评分双尺度

生成端的"回答质量"评分（区别于召回率）用 LLM 按要点打分，两套尺度：

- **rubric（宽泛）**：必答点意思对即给分——衡量"检索到 + 生成链路"的整体可用性；
- **strict（严格）**：必答点要求与参考要点 BERT 语义相似度 ≥85%——衡量精确性；

每题生成 3 次取最高分（`--runs 3`），控制生成方差；评分结果跨策略预评分复用，避免重复 LLM 调用。

### 3.5 Multi-Query 融合实验：一个诚实的负结果

验证过一个流行方向：LLM 为每题生成 3 个改写查询，与原查询共 4 路检索结果做 RRF 融合，对比单查询 direct 基线。结果（143 题，3 个切分器）：

| 切分器 | direct | Multi-Query | Δ |
|--------|--------|-------------|---|
| 1100_ovl150 | 79.0% | 78.3% | -0.7pp |
| 1500 | 80.4% | 79.7% | -0.7pp |
| 1500_ovl200 | 81.1% | 81.1% | 0.0pp |

**没有任何提升**。分析：召回率的瓶颈不在查询表述的多样性，而在块内容的语义完整性——查询改写生成的变体与原查询高度语义重叠，RRF 融合带不来新命中。这个负结果的价值在于：**排除一个方向，比盲目堆一个方向更省未来的钱。**

## 4. 核心结论与洞察

### 4.1 2×2 矩阵：内容召回率（112 题高质量测试集，hybrid top-5）

|  | 元数据注入 | 无元数据 |
|---|---|---|
| **章节预切** | 68.8% | 68.8% |
| **全文直切** | **84.8%** | 82.1% |

### 4.2 效应分解

| 效应 | 数值 |
|------|------|
| 切分方式效应 @有元数据（raw − meta） | **+16.0pp** |
| 切分方式效应 @无元数据（raw_pure − pure） | **+13.3pp** |
| 元数据效应 @章节预切（meta − pure） | +0.0pp |
| 元数据效应 @全文直切（raw_meta − raw_pure） | +2.7pp |

### 4.3 更大规模交叉验证

- **143 题集**：`fixed_1100_ovl150` 下元数据效应 +0.7pp（79.7% vs 79.0%）；`fixed_1500` 79.7% → `fixed_1500_ovl200` 81.1%，重叠窗口自身带来 +1.4pp——比元数据的贡献还大。
- **183 题汇总集**：全文直切下元数据净效应 +2.2pp（55.2% vs 53.0%），题面级别统计：7 题正效应、3 题负效应。
- 综合：**切分方式主导（+13~16pp），元数据影响次要（0~+2.7pp），最佳组合 raw_meta（84.8%）**。元数据的微弱贡献方向一致、大小稳定，说明它不是噪声——只是量级远不如切分方式。

### 4.4 为什么章节预切反而差？

这是整个研究最有意思的问题。逐题分析后，原因收敛到三点：

1. **答案粒度在"条"，而章节预切把每条切成一块**。条文短，大量块不足最小长度被丢弃——**切得越"结构正确"，丢的内容越多**；
2. **政策条文互相引用**（"按照第三章第七条执行"）。答案的语义内容横跨章节边界，章节硬边界恰好切断了这种引用关系；全文直切用固定窗口 + 重叠，反而保留了跨节上下文的连续性；
3. 章节预切产生的**块长度极度不均匀**（几十字到几千字），embedding 质量与检索排序对块长度敏感。

一句话：**"尊重结构"的切分服务于人类阅读，但不一定服务于向量检索。**

### 4.5 为什么元数据收益小？

注入的元数据（20-40 字章节摘要、100-150 字文件摘要）与块内容一起向量化后，被几百字的正文语义淹没；而 dense 检索匹配的是查询-块语义相似度，摘要带来的增量信号有限。**当切分已经把语义切碎时，元数据救不回来；当切分完好时，元数据只是锦上添花。** 这解释了为什么元数据效应只在"全文直切"这一侧为正——它弥补不了切分的结构性损失。

### 4.6 方法论结论（比数值结论更重要）

1. **先测量，后假设。** "结构化信息对 RAG 有帮助"是直觉，不是事实。把它变成可证伪的实验问题的那一刻，才是研究真正开始的地方。
2. **控制变量优于堆架构。** 分层路由系统做了整整一个阶段，不如一个 2×2 矩阵两条曲线有说服力。
3. **测量仪器本身要校验。** autojunk 伪影差点让所有结论失真。
4. **负结果要诚实公布。** Multi-Query 没效果，就写"没效果"，并给出解释。这比声称它有效更能说明研究者可信。
5. **效应量级 > 显著性方向。** +2.7pp 的元数据效应方向稳定，但量级决定它不值得成为一个复杂子系统。

## 5. 系统架构

```
测试集 xlsx ──prepare──▶ 评分要点（必答点/选答点/参考文件）
                              │
documents/{kb}/*.md ──章节检测──▶ 切分器(13 个, YAML 注册)
        │                          │
        │              dense（embedding 可插拔）+ sparse（BM25 jieba 词表）
        │                          │
        │           元数据注入（file_type/file_summary/section_summary，可选）
        │                          ▼
        │              Qdrant: {kb}__{chunker} collection
        ▼                          │
   检索（vector / bm25 / hybrid=Qdrant 原生 RRF）
                                   ▼
                    ┌──────────────┼────────────────┐
                    ▼              ▼                ▼
             生成回答(LLM)    召回率四口径      HTML 报告(Plotly)
                    ▼         （单块/合并/拼接/文件）
             评分(LLM, rubric/strict)
```

### 模块职责

| 模块 | 职责 |
|------|------|
| `main.py` | CLI 统一入口：strategies / build / search / experiment(run+recall) / mq-recall / prepare / compare / report-summary |
| `strategies.yaml` | 切分器/检索器/重排器声明式注册（新增策略零框架改动） |
| `core/registry.py` | YAML 驱动的动态类加载（工厂模式） |
| `core/section_meta.py` | 章节检测（Markdown 标题 + 中文序号正则）+ LLM 元数据生成（含 5 模型失败回退链） |
| `core/custom_splitters.py` | LLMIndexSplitter / ParentChildSplitter |
| `core/embedding.py` | 可插拔 embedding：本地 BGE（零密钥）/ 阿里云 / 自托管 vLLM |
| `core/sparse_encoder.py` | jieba 分词 + BM25 稀疏向量，词表拟合/持久化 |
| `core/qdrant.py` | Qdrant 封装 + 原生 RRF 混合检索（Prefetch + FusionQuery） |
| `builders/` | 单策略构建（chunk_index）+ 多策略并行编排（orchestrator） |
| `search/` | 检索策略抽象（flat：直接 chunk 级检索） |
| `pipeline/` | recall（四口径）/ scoring（双尺度评分）/ experiment（编排）/ multi_query / report（HTML） |
| `tools/` | prepare（要点提取）/ compare（策略差异定位） |
| `web_search.py` | Flask 单题检索可视化调试界面 |

### 工程取舍

- **YAML 声明式注册**：策略是数据不是代码。所有实验维度都从 YAML 展开，对比实验的展开、执行、汇总全程自动化；
- **dense+sparse 双向量 + Qdrant 原生 RRF**：混合检索在服务端完成（`Prefetch` + `FusionQuery`），避免 Python 侧搬动大规模候选集再融合；
- **429 退避与并发控制**：嵌入批次、upsert 批次、构建/生成/评分三级并发参数化；元数据与嵌入失败自动重试（上限 30 次）；
- **模型回退链**：元数据生成 LLM 主模型失败后依次尝试 5 个备选模型，保证批量构建不因单点失败中断；
- **零密钥默认路径**：`EMBED_SOURCE=local`（本地 BGE）+ `--pure` 构建 + recall 实验，全程不需要任何 API key，供 clone 后即跑通（见 §6）。

## 6. 快速开始（零密钥 demo）

```bash
# 0. 依赖与向量库（Qdrant 服务模式）
pip install -r requirements.txt
docker run -p 6333:6333 -d qdrant/qdrant

# 1. 生成示例知识库（4 个自编通用政策样式文档）+ 15 题样例测试集
python examples/generate_demo_data.py

# 2. 构建知识库（--pure：跳过 LLM 元数据生成；本地 BGE 无需任何 key）
python main.py build --kb demo --pure --parallel 2

# 3. 单题检索
python main.py search "文档密级如何划分" --kb demo --chunker fixed_1100 --retriever hybrid

# 4. 纯召回率对比实验（无 LLM 调用，产 recall.xlsx + HTML 报告）
python main.py experiment recall --kb demo --test-set examples/demo_testset.xlsx \
    --variable chunker --chunkers fixed_1100,fixed_1500

# 5. 汇总报告（扫描所有策略结果，生成统一对比 index.html）
python main.py report-summary output/demo
```

## 8. 已知限制与未竟方向

**已知限制（有意不修 / 如实声明）**：

- `--variable reranker` 是空转维度：检索/生成链路从不同调用 compressors，各 reranker 结果与 direct 相同。保留它是为了注册表完整性，README 里把它说清楚而不是藏起来；
- 检索策略只实现了 `flat`（chunk 直接检索）；分层路由（doc/sec 路由）在阶段三实验后**被有意放弃**，未在本仓库实现；
- `strategies.yaml` 中 `hybrid`/`hybrid_rrf` 的类定义（Python 侧加权/RRF 融合）与检索实际路径（Qdrant 原生 RRF）不一致——YAML 定义服务于 registry 直调场景；
- 报告 HTML 依赖 Plotly CDN，离线环境打不开；
- 全部结论基于**单一领域的政策法规语料**，外推行需谨慎——这正是 2×2 矩阵应该在不同语料上复现的原因。

**未竟方向**：

1. 表格密集文档的结构化切分（表格语义的保留远比分章节重要，是当前召回率天花板的主要来源）；
2. 元数据的正确用武之地可能是**路由型检索**（库规模大、多领域混合时的先验过滤），而不是块内容注入；
3. 查询侧增强换方向：Multi-Query 已被证伪，值得验证的是 HyDE 或针对"条文引用"的查询扩充；
4. 章节级 RAG：块内引用的跨条补齐（"按照 X 条执行"的自动展开）。
